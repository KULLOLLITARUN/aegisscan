### P2 — design decisions / nice to have
12. **Multi-credential pooling** (plan V5) is not implemented. Verify Groq's ToS before adding.
13. **Prompt-injection defence is mitigation, not proof.** No adversarial test corpus exists that exercises a real model. Add a set of injection samples and assert the model output still reports the real vulnerability.
14. **Done: non-code prompt text is fenced and sanitised.** `build_user_prompt` now puts static findings inside their own random `STATIC-<hex>` fence (code fence stays first) and passes every non-code string (file name, language, symbol, static issue type / explanation / rule source) through `_one_line`: redact with the scan's privacy mode, drop control characters, collapse all whitespace to one line, truncate (120/300 chars). This closed a wider hole than the item described: a file name with newlines could start a fake `## SYSTEM` line in the prompt, and Semgrep messages can interpolate scanned code. The system prompt now declares the static list untrusted too. Tests in `tests/test_v11_hardening.py`. This is mitigation, not proof (see item 13): nothing here was run against a live model.
15. **Done: `--changed-only` tested end to end, and a bug fixed.** Found by running it on a real temp repo: the filter only applied to chunking/LLM, so static findings in *unchanged* files were still reported (a PR would be blamed for every old finding, and a CI gate would fail on them). `run()` now drops static findings outside the changed set. `tests/test_v21_changed_only.py` (7 tests, fake static tools, real git): flag on/off, untracked + staged files, clean repo scans nothing, non-git folder falls back to a full scan, repo with no commits (`git diff HEAD` fails, `git status` still used), flag parsing; 3 of them fail without the fix. **Limitation kept:** Bandit/Semgrep/Gitleaks still scan the whole tree, so this fixes correctness, not speed (HOW_IT_WORKS.md corrected; it claimed CI "only pays for what changed"). Making the tools scan only changed files would be the speed fix. Environment note: `C:/Users/Kullo` is itself a git repository, so temp dirs under it look like part of a repo; tests that need "not a repo" set `GIT_CEILING_DIRECTORIES`.
16. **Line endings: done.** `.gitattributes` pins `* text=auto eol=lf` (index was already all LF; `git add --renormalize .` changed nothing), `.bat/.cmd/.ps1` stay CRLF, images are binary. Existing CRLF working-tree files (76 at the time) do not show as modified, and each one still prints a harmless "CRLF will be replaced by LF" warning when staged until it is rewritten with LF (any editor that keeps LF, or a fresh checkout). To convert them all now: commit/stash, then `git rm --cached -r . -q && git reset --hard` (destructive to uncommitted work; ask first).
17. **Done: stale `.security-baseline.json` deleted** (still in git history). It was inert (only read with `--baseline`), held a machine-specific absolute path, and could only match on that one path (see item 19). 13 of its 14 fingerprints still matched a fresh scan, so it was not stale by content. README now describes `--save-baseline` / `--baseline` instead of naming the file.
18. **Done: Groq model rot is handled at runtime.** `GroqProvider` calls `models.list()` once on first use (cached, failure-tolerant), drops configured models the key cannot use, and warns with available ids plus the `AEGISSCAN_GROQ_MODELS` hint if none are served. A model that still 404s is remembered as retired for the provider's lifetime, so a scan no longer pays the same 404 on every request (429 rate limits are not remembered). If everything is marked retired it retries instead of giving up. Verified with one real read-only `models.list()` call (no completion): 11 models served, all 3 configured models among them. `tests/test_v20_groq_model_rot.py` (8 tests, fake client). Still manual: the built-in default list itself needs updating when Groq retires models. The same kind of rot hit Semgrep (a renamed pack zeroed all results; now logged, see section 1). OpenAI/Ollama have no equivalent handling.
19. **Done: baselines are portable.** `fingerprint(finding, root)` now hashes the path relative to the scan target (slash-normalised), so a baseline saved in one checkout directory or OS matches in another. New baselines carry `fingerprint_version: 2`. Legacy baselines (no version field) still suppress on the machine and path that made them (the matcher accepts either form) and log a warning telling the user to re-create them; nothing breaks. Verified end to end: `--save-baseline` on one copy of `examples/vulnerable_python` (23 findings) then `--baseline` on a copy in a different directory suppressed all 23 (23 without it). Tests in `tests/test_intelligence.py`. Not tested: a baseline made on Windows applied on Linux (only different directories on one OS; path normalisation uses `as_posix`). A finding outside the scan root falls back to its own slash-normalised path.
20. **Investigated, no change: Semgrep language packs do not help on the multilang corpus.** All four ids (`p/java`, `p/golang`, `p/php`, `p/csharp`) are valid on the live registry, but adding them left the benchmark byte-for-byte identical (Semgrep 44/52 correct, precision 86.13%, in-scope recall 81.98%): every line they report is already caught by the existing packs (SQLi, MD5, BinaryFormatter, PHP echo/exec) apart from two Go TLS notes. They still miss the same 11 labels (Java `Runtime.exec`/XXE, Go `exec.Command`, PHP LFI/unserialize/md5/eval, C# MD5/`Process.Start`/XXE, TS template-literal SQLi). Likely cause: Semgrep's taint rules need a recognised source (`request.getParameter`, `$_GET`...) and these samples pass input through plain method parameters, which is common in library code; some sinks (PHP `eval`/`unserialize`) simply have no rule in the packs. Not shipped, because it would add four more registry ids that can rot and extra download time for no measured gain. Options if this gap matters: write a few custom Semgrep rules that treat function parameters as tainted, or rely on the LLM pass for these languages (the labels list `llm` in `expected_by`). Re-check after a live LLM run (item 7a) to see whether the LLM closes the gap. (First live run: it closed 5 of the 11, but with wrong lines; re-check after the second run.)
21. **Done: dedupe prefers a static tool's exact location.** `deduplicate()` kept the highest-confidence finding per cluster (same file + category within 5 lines), so a slightly misplaced LLM finding could displace the correct Bandit/Semgrep one; the first live run lost static true positives this way. `_pick_best()` now keeps the static finding when the winner is an LLM finding and a static one is within `STATIC_LOCATION_MARGIN` (0.10) of its confidence (this includes exact ties, which the LLM used to win). A far more confident LLM finding still wins. The 0.10 margin is a judgement call, not fitted; static-only benchmark numbers are unchanged by construction, the effect on a live run is unmeasured. 4 tests in `tests/test_intelligence.py`.
22. **The LLM prompt has no line numbers.** The model cannot report lines it cannot see; `_locate_lines` works around it by matching the evidence snippet. Numbering the code in the prompt (and telling the model to cite them) would be more direct, but changes the fence format and the evidence contract, so measure it on a live run.
23. **`line_start`/`line_end` default to 1 in the LLM schema.** A model that omits them silently yields line 1. Should be required or `None` with an explicit "unlocated" path.
24. **`rate_limit_hits` in the benchmark report disagrees with the log.** The live run reported 0 while the log had 43 "rate limit ... failing over" warnings from `GroqProvider`. The counter and the failover path are not wired to the same event; unexplained, needs a look.
25. **Follow-ups noted:** OpenAI/Ollama have no model-rot handling like Groq's (item 18); `--changed-only` still runs Bandit/Semgrep/Gitleaks on the whole tree (item 15).

## 3. How to test

Always use the project venv. From the project root (`D:\AI_Projects\AI-Driven_Workspace_Security_&_Optimization_Scanner`):

```powershell
.venv\Scripts\python.exe -m pytest -q -o addopts="" -p no:cacheprovider
```

- Full suite takes ~90–110 s (several tests run Bandit/Semgrep on the examples).
- With coverage and the CI gate:

### Known environment quirks (Windows dev box)
- Git Bash heredocs containing many quotes can fail to parse; prefer writing scripts to files.
- `find`/`Glob` over the project descend into `.venv` and `ui/node_modules` — scope searches to `scanner`, `tests`, `examples`.
- Files use CRLF; when scripting edits preserve line endings.
- The project path contains `&` (`Security_&_Optimization`), so `npm run ...` fails under cmd.exe (npm reports `Cannot find module` for vite or oxlint). Call the tools through node instead: `node node_modules/vite/bin/vite.js build`, `node node_modules/oxlint/bin/oxlint`. Do not run `npm ci` here (it wipes node_modules and would hit the same problem).
- Semgrep zero-findings cause found and fixed: `p/owasp-top-10` no longer exists on the registry (HTTP 404, correct id `p/owasp-top-ten`), and one invalid config makes Semgrep exit 7 with no results, so all five packs were lost silently. The runner now logs Semgrep `errors` as warnings. With the fix, `--benchmark --static-only`: Semgrep 25/28 correct (89%), precision 87%, in-scope recall 88.9%, recall over all labels 83%. Remaining misses are mostly JS xss/injection labels that the p/javascript packs do not match. Watch for further registry renames (see P2 item 18).
- Fixed: the CLI crashed printing non-cp1252 characters (e.g. U+2011 in a finding) on a default Windows console. `main._make_console_safe()` now sets `errors="replace"` on stdout/stderr at startup.
- `main.py --benchmark` without `--static-only` makes live LLM requests (~75 per run).
